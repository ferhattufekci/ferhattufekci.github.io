# Engineering Assessment

**Scope:** the whole repository at `18004f4` (2026-11-10). **Method:** read the source, the
workflows, the tests and the CI history; run what can be run here; measure rather than assume.
Every claim carries its evidence level: **[D]** verified here, **[G]** observed in this
repository's CI or data, **[B]** vendor documentation, **[?]** not verified.

## 1. What this project is

A single-page static portfolio site served by GitHub Pages: `index.html` plus `css/`, `js/`
and a generated `data/` catalogue. There is **no backend, no database, no API of its own and
no authentication** [D]. Two scheduled workflows (`fetch-medium.yml`, `fetch-github.yml`)
read the author's Medium RSS feed and the GitHub REST API and commit the result into
`data/*.json`; the page fetches those files at runtime.

This matters for how the repository should be judged. Checklist items such as database
design, migrations, authorisation models, container scanning and service health checks have
no subject here. Inventing them would produce documents that describe nothing. They are
listed as *not applicable* in section 5 with the reason, rather than filled in.

What the repository does demonstrate instead is the part of the lifecycle that a static site
genuinely has: requirement traceability, a large browser test suite, a release pipeline with
an exact-SHA gate, a failure-recovery mechanism that is deliberately observe-only, and a
documented record of open technical debt.

## 3. Strengths found

These are the things a reviewer should look at first; each is verifiable in the repository.

1. **Requirement traceability is real, not decorative.** Every test title starts with an id
   (`R-RESUME-06 | Given Resume, then ...`). 211 ids are in use [D]. The matrix at
   `docs/business-analysis/requirements-traceability-matrix.md` is generated from the test
   files by `scripts/generate-rtm.mjs`, and `scripts/tests/rtm.test.js` fails when it drifts,
   so the document cannot quietly become fiction.
2. **Supply chain of the pipeline is pinned.** All 8 third-party actions are pinned to a
   commit SHA, not a tag [D]. Workflow permissions are least-privilege: `contents: read` at
   file level, `contents: write` only on the two fetcher jobs [D].
3. **Release integrity.** `pages.yml` resolves one immutable source SHA, tests that exact
   artifact, and the deploy job rejects a superseded release. The artifact bytes are verified
   again before production verification [D].
4. **Failure recovery is observe-only by default.** `scripts/ci/recovery.mjs` decides what it
   *would* do and records it; it acts only when the repository variable
   `PORTFOLIO_RECOVERY_ACT` is `true`, which is off [G]. Its 14 tests run the real command
   through a fake `gh`/`git` on a stripped `PATH` and include mutation checks that a
   dishonest report (`performed: true` when the action failed) is caught.
5. **Tests are written to fail for the right reason.** Several suites carry explicit mutation
   checks, i.e. the test is proven to detect a planted regression instead of being assumed to.

## 4. Findings

Ordered by consequence. "Fixed here" means in this change; the rest are recorded, not papered over.

### F-1 Unvalidated URL scheme at the third-party trust boundary — **fixed here**
`index.html` assigns feed values directly to the DOM: `link.href = art.url` and
`image.src = art.thumbnail` [D]. Those values came from the Medium RSS feed with no scheme
check, so a `javascript:` link in the feed would have become an executing href. The feed is
the author's own account, so exploitation was unlikely, but the boundary was unguarded.
Fixed at generation time in `scripts/lib/safe-url.mjs`, applied in `fetch-medium.js`
(`url`, `thumbnail`) and `fetch-github.js` (`homepage`), with
`scripts/tests/data-contract.test.js` enforcing the invariant on the committed data and
rejecting obfuscated schemes (`java\tscript:`, leading control characters, `data:`, `blob:`).
Two mutations were planted and both were caught [D].

### F-2 No Content-Security-Policy — **not fixed, deliberately**
The site ships no CSP [D]. A CSP is the control that would have made F-1 unexploitable in
depth. It is not added here because the page still carries large inline `<script>` blocks and
inline event attributes; any policy strong enough to matter would need `'unsafe-inline'`,
which makes it theatre, or hashes/nonces for every block, which GitHub Pages cannot serve as
headers and which would have to go in a `<meta>` tag and would break on every edit. The
honest sequence is: finish the inline-script extraction (A0 is merged, A1+ is planned in
`docs/T-4-INLINE-SCRIPTS.md`), then add a CSP that does not need `'unsafe-inline'`. Tracked
in `docs/OPEN-ITEMS.md`.

### F-3 No dependency or secret scanning in CI
There is no `npm audit` step, no Dependabot configuration and no secret scan [D]. The blast
radius is small (6 devDependencies, no runtime dependencies shipped to the browser except
vendored jQuery/Modernizr) but the control is missing. Recommended, not added here, because
adding a gate that can fail on an upstream advisory is a pipeline-policy decision.

### F-4 `index.html` concentrates behaviour that belongs in modules
Roughly a quarter of the file is inline script: blog rendering, project rendering, language
and category filters, analytics. This is the main structural debt. It is already under
characterization tests (`tests/browser/inline-script-contract.spec.mjs`, 21 tests, A0) so the
extraction can be proven behaviour-preserving. Plan: `docs/T-4-INLINE-SCRIPTS.md`.

### F-5 No type checking
No TypeScript and no `checkJs`. A `tsc --checkJs` gate over `scripts/` and `js/` would catch
a real class of error cheaply. Not added here: it needs a new devDependency, and the standing
instruction for this repository is no new dependencies without agreement.

### F-6 Browser job deadlines were the actual CI failure mode
Run `42796215632` was red not because a test failed but because the browser shard hit its
40-minute job deadline at test 767/801 and the keyboard job hit 50 minutes at 621/658 [G].
Per-test time had roughly doubled against 2026-11-08 for the same specs [G]. Deadlines were
raised to 60/75 minutes (PR #46, merged). The cause of the slowdown is **[?]**; the same
pages measured the same locally in Chromium, so hosted-runner variance is the working
hypothesis, not a conclusion. Shards are partitioned by file count, not duration — real
rebalancing is still open.

### F-7 Two unexplained test failures
`R-FILTER-04` (twice, small-mobile, shard 2/2) and `R-KEYBOARD-01` (WebKit/Firefox, several
runs, a different element each time) [G]. Neither root cause is proven; traces were not
obtainable within this environment's network allow-list. Recorded in `docs/OPEN-ITEMS.md`
(RF, RK-01). No assertion was weakened and no retry was added to hide them.

### F-8 Repository hygiene
`README.md` states licence terms but there is no `LICENSE` file, and there is no
`SECURITY.md` [D]. `TEST-STRATEGY.md` sits at the repository root while the rest of the
documentation is under `docs/`. Low severity, listed for completeness.

## 5. Checklist items that do not apply, and why

| Item | Why not |
|---|---|
| Database design, migrations | No database. Content is JSON generated from two public sources. |
| API design, API tests | The site exposes no API. `scripts/verify-agent-endpoints.mjs` checks the *published static endpoints* (`llms.txt`, `sitemap.xml`, agent content), which is the closest real equivalent and already exists. |
| Authentication / authorisation | No accounts, no sessions, no server. |
| Docker / Docker Compose / container scanning | The deployable artifact is a static bundle for GitHub Pages. A container would add a build surface with no consumer. |
| Secret management | The pipeline uses only the ephemeral `GITHUB_TOKEN`; no secrets are configured and none are needed [D]. |
| Staging environment | GitHub Pages serves one site. PR runs build and test the artifact without publishing, which is the available equivalent. |
| CSRF | No state-changing requests exist. |

## 6. Priorities

1. Resolve F-7 (needs trace access) — reliability of the suite is the gate on everything else.
2. Rebalance browser shards by measured duration (F-6).
3. Continue the inline-script extraction (F-4), then add a CSP that needs no `'unsafe-inline'` (F-2).
4. Add dependency scanning (F-3) and a type-check gate (F-5), each as its own decision.
5. Hygiene: `LICENSE`, `SECURITY.md`, move `TEST-STRATEGY.md` under `docs/testing/` (F-8).
