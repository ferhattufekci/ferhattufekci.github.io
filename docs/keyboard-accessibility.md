# Keyboard and touch interaction audit

The acceptance criteria are keyboard operation, meaningful focus order, visible and unobscured focus, and native accessible names/states. Automated checks support these criteria; they do not establish complete WCAG 2.2 AA conformance or replace assistive technology and real-device testing.

## Verified problems and fixes

| Component | Reproduction and cause | Result |
| --- | --- | --- |
| Fixed previous/next arrows | A real emulated touch leaves `:hover` matched after navigation. Unconditional rules in `main.css` and the later dark theme change the icon color to the accent; neither focus nor a selected class caused it. The original `div` controls were also absent from the Tab order and appeared before the content in document order. | Native named buttons after `main`; capability-gated hover, limited pointer-modality tracking on this group for hybrid devices, native press feedback, and a distinct keyboard outline. Circular navigation and touch dimensions are preserved. |
| Contact interview and links | Tab to either external link. An inline anchor wrapped a block `h3`, creating fragmented focus painting near the icon instead of a single text box. Phone and email used the opposite nesting. | All four headings contain their links. Inline-block links paint one focus rectangle around the complete text and external-link icon. |
| Section entry | Entering through menu, initial hash, or history produced different focus positions; subsequent Tab could start in the sidebar or late in the content. | Explicit section entry focuses its heading (`tabindex=-1`); the next Tab follows the visible control strip. Keyboard arrow navigation retains the arrow. History repairs focus when the previous element becomes hidden. Filters keep focus on their controls. |
| Shared focus styling | Legacy global anchor focus resets and later component styles hid or weakened focus. | A final shared `keyboard.css` uses existing theme tokens and `:focus-visible`. Inset outlines protect controls inside clipped panels. Selected, hover, press and keyboard focus remain separate states. |
| Mobile navigation | Keyboard opening tried to focus a link while its inherited transition visibility was still hidden. `.header * { transition: all ... }` also delayed descendant visibility after the reduced-motion drawer itself had opened; this was reproduced in WebKit and caught by Ubuntu CI. Closing by resize or the non-focusable backdrop lost focus on `body` because those paths never requested restoration. | Limit descendant transitions to visual properties, excluding inherited visibility, and honor reduced motion for descendants. Focus the first link after the existing drawer transition helper resolves. Cancellation closes the pending operation. Escape, resize and backdrop dismissal return lost drawer focus to the visible toggle; activation of another focusable control preserves that control's focus. Ordinary navigation has no artificial focus trap. |
| Scroll regions and filters | Firefox automatically put horizontally overflowing filter lists into the Tab order before their buttons, with an unnamed browser-default outline. About's independent scroll area was similarly unnamed. | Filter list containers use `tabindex=-1`; their native buttons remain sequentially reachable. About has a named keyboard-scrollable region, consistent with the other content panels. |
| Resume information/disclosures | Closing the information tip called `blur()`. | Closing retains the trigger's focus; a suppression state dismisses the preview until the next legitimate entry. Native `details/summary` behavior stays intact. Section shortcuts focus only their target, allowing navigation to continue within it. |
| Starred projects | The final Show More operation hid its currently focused button. | On the final batch only, focus moves to the first newly appended card link. Intermediate batches retain the button. |
| Optional booking widget | The owned dismiss control was a click-only `div` nested in the vendor control and installed after a fixed delay. | A named sibling button works with native Enter/Space. Mount observation disconnects after discovery; dismissal restores focus before hiding its subtree. |
| Repeated navigation | No consistent first keyboard stop bypassed the shell. | A first-body Skip to content link works in the SPA and generated independent documents without corrupting routing. |

## Regression checks

`keyboard-accessibility.spec.mjs` traverses the actual Tab/Shift+Tab sequence on About, Resume, Blog, Projects, Contact, standalone About/Contact/Privacy and 404. It compares all visible sequential controls with the visited controls, checks computed focus outlines and viewport obstruction, and exercises native Enter/Space, menus, filters, disclosures, history, final pagination and skip links. Both theme variants, desktop/mobile layouts, both motion preferences, enlarged text and CSS zoom are covered. CSS zoom is not a claim of testing the browser's native zoom UI.

`arrow-controls.spec.mjs` verifies touch before/after transitions without an intervening click, blur or mouse movement; both arrows, repeated circular navigation, theme changes, hover, keyboard operation and cancelled presses. `arrow-hybrid.spec.mjs` uses trusted Chromium touch/pointer cancellation followed by a real mouse move. Assertions compare computed color/background/border/outline, not only classes. The old released artifact fails the touch regression.

The existing Chromium matrix runs the new checks alongside the full suite. The mandatory **Cross-browser Keyboard Tests** job downloads and verifies the same immutable artifact, runs the keyboard checks in Firefox/WebKit at both viewport widths and themes, and runs the WebKit touch-arrow matrix. Its result is required by the quality gate. The final production smoke separately checks live data, pinned control panels, native keyboard entry, Contact link geometry, arrow reachability/focus and mobile touch restoration.

Local Windows WebKit's default keyboard behavior was independently reproduced on a minimal page: plain Tab skipped native anchors while reaching buttons. No website `tabindex` workaround or weakened assertion was added for this browser setting. Ubuntu CI is the authoritative WebKit keyboard execution; report local results separately. Real iOS/Android devices, screen readers and native browser zoom require separate manual checks. Existing unrelated accessibility debt remains tracked by the pre-existing accessibility baseline; this change does not certify the whole site.
